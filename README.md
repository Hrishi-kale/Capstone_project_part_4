# SOC Automation Toolkit

Three small, dependency-light Python tools for reducing analyst workload:

1. **`port_scanner.py`** — multithreaded TCP port scanner with banner grabbing (stdlib only).
2. **`log_enricher.py`** / **`virustotal_check.py`** — extract IPs from logs and enrich them with threat intel.
3. **`ml_threat_detector.py`** — trains and evaluates a supervised and an unsupervised model on a labelled phishing dataset.

## Task 1 — `port_scanner.py`

Uses only `socket` and `threading` — no `nmap`, no shelling out to external scanners.

```bash
python3 port_scanner.py <target_ip> <start_port>-<end_port> [--timeout SECONDS] [--workers N]

# Example
python3 port_scanner.py 127.0.0.1 1-1024 --timeout 0.5
```

**Design decisions:**
- A `threading.Semaphore` caps concurrently live threads (default 200) so a large range like `1-65535` doesn't spawn tens of thousands of OS threads at once.
- A `threading.Lock` guards every append to the shared `results` list — without it, two threads finishing at the same instant could interleave their `list.append()` calls and corrupt or drop results.
- Banner grabbing is two-step: try a bare `recv()` first (services like SSH/FTP/SMTP announce themselves unprompted), and only if that returns nothing, send the generic `\r\n` probe and try once more. Each step has its own `try/except`, so a timeout on the first `recv()` doesn't prevent the probe-and-retry from running.
- `connect_ex()` (not `connect()` + exception) is used for the initial connection attempt so a closed port is just a nonzero errno, not a raised exception, keeping the common case cheap.
- Closed, filtered, and refused ports are all caught and silently skipped — the scanner never crashes on them.

Tested locally against a throwaway TCP server that mimics an SSH banner, plus closed-port ranges and an invalid target — all handled without crashing.

## Task 2 — `log_enricher.py`

```bash
python3 log_enricher.py sample_logs/sample.log
```

**Design decisions:**
- IPv4 addresses are found with `re.compile(r"\b(?:\d{1,3}\.){3}\d{1,3}\b")` — a *syntactic* match. Semantic validation (rejecting `999.999.999.999`, private ranges, loopback, link-local, CGNAT) is delegated to Python's `ipaddress` module, which is far less error-prone than trying to hand-encode all of RFC 1918 into the regex.
- Deduplication uses a `set`.
- Each IP is looked up at `http://ip-api.com/json/<ip>` via `requests`; a 1.5-second delay between calls keeps a large log file under ip-api.com's free-tier rate limit (45 req/min).
- HTTP failures, non-2xx responses, malformed JSON, and API-level failure statuses are all caught and returned as `{"error": "..."}` for that IP rather than raising — one bad lookup can't take down the whole run.

## Task 4 — `virustotal_check.py`

```bash
export VT_API_KEY="your-key-here"
python3 virustotal_check.py sample_logs/sample.log
```

- The API key is read exclusively from the `VT_API_KEY` environment variable via `os.environ.get`. If it isn't set, the script exits immediately with a clear message instead of sending an unauthenticated request. It is never hardcoded, and `.env` is excluded from version control by `.gitignore`.
- `401` (bad key), `404` (IP not found), and `429` (rate limited) are each caught and turned into a friendly `{"error": "..."}` message; generic network errors and unexpected response shapes are caught too.
- Reuses `extract_public_ips()` from `log_enricher.py` so both scripts agree on what counts as a "unique public IP."

### Input → Process → Output

The "Input → Process → Output" automation mindset means designing each tool around one clear, testable transformation: take a well-defined input, apply a deterministic process to it, and produce a structured output another tool (or a human) can act on — instead of one tangled script that does everything. `port_scanner.py` maps to this as Input = target IP/port range, Process = concurrent TCP connect attempts + banner grabs, Output = a port/state/banner table. `log_enricher.py` maps to Input = a raw log file, Process = regex extraction + private-IP filtering + ip-api.com lookups, Output = a JSON dictionary of enriched IPs. `virustotal_check.py` follows the same shape with VirusTotal as the enrichment source, and `ml_threat_detector.py` closes the loop with Input = an enriched/labelled observation, Process = trained model inference, Output = a benign/malicious classification.

### Preprocessing

- **Null rows removed: 0** (dataset has none; the `dropna()` step is still run as a safety net).
- **Duplicate rows removed: 5,206** — most features are low-cardinality (`-1`/`0`/`1`), so many distinct sites end up with identical feature vectors. Removing them leaves **5,849 rows**, still comfortably above the assignment's 5,000-sample minimum. Post-dedup split: 3,019 phishing(-1) / 2,830 legitimate(1).
- **Categorical encoding:** all 30 feature columns are already integer-encoded, so `pd.get_dummies` is a no-op here — it's included so the pipeline generalizes to other labelled security datasets that do carry string categoricals.
- **Class distribution:** see the "Class distribution" section above (pre-dedup: 6,157 legitimate / 4,898 phishing; post-dedup: 2,830 legitimate / 3,019 phishing).
- **Split:** 80/20 train/test via `train_test_split(..., random_state=42, stratify=y)`.

### Isolation Forest — anomaly detection

The task instructs treating the **minority class as the anomaly class**. In the original, pre-deduplication dataset, phishing(-1) is the minority class (4,898 of 11,055 samples, 44.3% — see "Class distribution" above), so phishing is treated as the modeled anomaly throughout, and the `contamination` parameter is estimated from the phishing proportion in the training set. Deduplication happens to leave the remaining 5,849 rows close to balanced (51.6% phishing / 48.4% legitimate — see "Preprocessing" above), so "minority" no longer applies in a strict post-preprocessing sense; this is a deliberate design choice based on the dataset's original class proportions and the standard SOC convention of treating malicious activity as the class of interest, not a literal recomputation of minority status after dedup. `IsolationForest`'s `contamination` parameter only accepts values in `(0, 0.5]`, so the estimate is clipped to `0.5`. Trained on `X_train` only (never sees labels); `IsolationForest.predict()` conveniently returns `1`/`-1` in the same convention as this dataset's own label, so no remapping was needed before scoring against `y_test`.

- Accuracy: **0.4410**
- Precision (phishing class): **0.4576**
- Recall (phishing class): **0.4470**
- F1 score: **0.4523**

### Model comparison

| Model | Accuracy | Precision | Recall | F1 Score | Notes |
|---|---|---|---|---|---|
| Random Forest (supervised) | 0.9419 | 0.9467 | 0.9404 | 0.9435 | Trained on labelled data; precision/recall computed for the phishing(-1) class |
| Isolation Forest (unsupervised) | 0.4410 | 0.4576 | 0.4470 | 0.4523 | Never saw labels during training; contamination clipped to 0.5 (train-set phishing proportion) |

The gap is expected and is itself informative: Isolation Forest has no access to labels and can only flag points that look statistically unusual in feature space, which doesn't line up well with a near-balanced, low-cardinality tabular dataset like this one, where "phishing" and "legitimate" sites aren't necessarily geometric outliers of each other.

### Discussion (precision/recall vs. accuracy, F1, and limitations)

In a security dataset like this one, the two classes are rarely evenly weighted in the real world — malicious traffic is usually a small fraction of total traffic — so a model that just predicts the majority class every time can still post a deceptively high accuracy score while missing nearly all real threats. Precision tells an analyst what fraction of the alerts flagged as malicious were actually malicious; low precision means analysts waste time chasing false alarms. Recall tells them what fraction of actual threats the model caught; low recall means real attacks slip through undetected. The F1 score is the harmonic mean of precision and recall, and it is useful because it penalizes models that trade one off heavily for the other, giving a single number that only looks good when both are reasonably balanced. The Random Forest's main limitation is that it can only recognize patterns similar to what it was trained on, so novel attack techniques absent from the training data will likely be missed. Isolation Forest's limitation is that it flags anything statistically unusual as an anomaly, including rare-but-legitimate behavior, which tends to produce a high false-positive rate in a live SOC.

## SOAR workflow integration

The three tools map cleanly onto standard SOAR pipeline stages. `port_scanner.py` handles **data collection**: it produces raw, structured facts about a host's exposed attack surface (open ports and service banners) that downstream stages consume. `log_enricher.py`, together with `virustotal_check.py`, handles **enrichment**: it takes low-context raw log lines, extracts the IPs worth investigating, and attaches geolocation, ISP, hosting/proxy/VPN flags, and reputation scores from ip-api.com and VirusTotal so an analyst or downstream logic has real context instead of a bare IP address. The ML threat detector handles **detection**: it takes an enriched observation and outputs a classification (or, via `predict_proba`, a confidence score) estimating how likely the observation is malicious.

In an automated pipeline, that confidence score decides the next branch. A high-confidence malicious classification, roughly above 0.90–0.95 and corroborated by independent signals such as multiple VirusTotal vendor detections, can trigger an **automated response** like blocking the IP at the firewall, because the cost of a false positive (briefly blocking a legitimate IP) is low relative to missing a real intrusion. Mid-range confidence, roughly 0.5–0.9, should route to a **human analyst** rather than auto-blocking, since acting on an uncertain call risks disrupting legitimate traffic. Low-confidence or benign classifications are simply logged. Where exactly that threshold sits is a genuine trade-off a SOC must tune deliberately: set it too low and false positives erode analyst trust and cause outages; set it too high and real threats go unblocked while waiting on review.
